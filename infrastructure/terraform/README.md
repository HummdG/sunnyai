# Infrastructure

Terraform for the Sunny API on Google Cloud.

> **Status: written, never applied.** No GCP project has been provisioned, no
> `terraform init`, `plan` or `apply` has been run against this configuration,
> and no binary is installed in the development environment it was authored in.
> The CI job runs `fmt -check` and `validate -backend=false`, and **that job is
> the first real check this configuration has had**. Treat it as a description of
> intent that compiles, not as infrastructure known to work.

## What it creates

| Resource                     | Why                                                                                |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| Cloud Run v2 service         | Runs the API container. Stateless, so it scales horizontally with no coordination. |
| Artifact Registry repository | Holds the API images.                                                              |
| Service account              | The runtime identity. Least privilege: it can read two secrets and nothing else.   |
| Secret Manager secrets       | One for the model credential, one for the session secret.                          |
| `random_password`            | The session secret's value, generated per environment.                             |

It does **not** create a database. The API currently persists to a file store
(`apps/api/src/store.ts`); the managed database is a decision that has not been
made, and inventing one here would be a decision made by a Terraform file rather
than by a person. See `docs/architecture/adr-006-data-and-consent.md`.

## No credential passes through state

Terraform state is readable by anyone with access to the state bucket. A model
credential written into it is a credential that leaked. So the key secret is
created **empty** and its value is added out of band:

```bash
printf '%s' "$GEMINI_API_KEY" | gcloud secrets versions add sunny-gemini-api-key \
  --project "$PROJECT_ID" --data-file=-
```

The session secret is the exception, and deliberately so: it is generated _by_
Terraform, and it is a value that exists only to sign this deployment's own
sessions. Losing it invalidates live sessions; leaking it is worse than a
re-deploy. It is regenerated by tainting `random_password.session_secret`.

## Applying

```bash
cd infrastructure/terraform

terraform init \
  -backend-config="bucket=$TF_STATE_BUCKET" \
  -backend-config="prefix=sunny/$ENVIRONMENT"

terraform plan -var-file="env/$ENVIRONMENT.tfvars"
terraform apply -var-file="env/$ENVIRONMENT.tfvars"
```

`env/*.tfvars` is **not** committed. It names a real project and a real image,
and it is environment-specific by definition. Only `env/example.tfvars.example`
is in the repository.

## The image is deployed by CI, not by Terraform

`ignore_changes` is set on the container image. CI builds a tag and deploys it;
without that lifecycle rule, the next `terraform apply` would silently roll the
service back to whatever `api_image` said the last time a human ran it. Terraform
owns everything _around_ the image, which is the part worth reviewing.

## Not covered here

- **The application-load-balancer / CDN layer.** Not needed until there is
  traffic to balance, and the SSE caveat in ADR-002 has to be settled first:
  whether a proxy buffers a streamed response is not something to discover after
  go-live.
- **The marketing site and the dashboard.** Not built yet.
- **Monitoring and alerting.** `/healthz` reports capability, and nothing reads
  it yet. Until something does, a dead model key is a silent failure.
- **The Terraform state bucket.** Bootstrap it by hand once per environment;
  Terraform cannot create the bucket that holds its own state.
