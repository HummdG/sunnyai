# ADR-005: Widget confinement — Shadow DOM, a closed vocabulary, text-only output, and a landmark allow-list

- **Status:** Accepted
- **Date:** 2026-10-10
- **Related:** ADR-001 (platform), ADR-002 (hosting), ADR-003 (tools)

## Context

The widget runs **inside someone else's web page** — an installer's site — which
is the least trusted environment in the system. Four distinct hazards follow, and
each needs its own control:

1. **Style collision.** The host's CSS must not restyle Sunny, and Sunny's CSS must
   not leak out.
2. **The model must not become client behaviour.** If a model response could name
   an animation, a script, a selector or a URL, the model would be driving the
   customer's page.
3. **Model output is untrusted text.** It has to be rendered, never executed.
4. **`suggest_page_action` must not become arbitrary DOM or arbitrary URLs.** A
   tool that points at things on the host page is a tool that could otherwise
   reach anything on it.

The plan (§6.2) says "Isolate CSS/JS via iframe or Shadow DOM" and (§8, §9) that
website guidance must use "an allowlist of named targets/actions" with "no
arbitrary model-generated JavaScript, unrestricted selectors, credential access or
silent form submissions". This ADR records how the code does each.

## Decision

### 1. Everything lives in one shadow root

The widget attaches an **open** shadow root and builds its entire UI inside it
(`packages/widget/src/widget.ts`, `host.attachShadow({ mode: 'open' })`). The
host element is "a bare marker: every style the widget needs is inside the shadow
root, so the page's own CSS cannot collide with it"
(`packages/widget/src/index.ts`). Styles are injected as a single `<style>` inside
the shadow root (`widget.ts`, `#buildShell`; `packages/widget/src/styles.ts`).

Mode is **`open`, deliberately**: the comment states the isolation "comes from the
shadow boundary, not from secrecy" — an open root lets the host page drive the
widget programmatically and lets an accessibility audit see into it. The two
things that cross the boundary are the accent colour, set through a CSS custom
property on the host element (`--sunny-primary-color`, `#applyConfig`), and text
the widget created itself.

The host page is given a small, stable handle — `window.sunny.open()/close()` and
the widget list — and nothing that "could be used to drive it from outside the
approved vocabulary" (`packages/widget/src/index.ts`).

### 2. The prop vocabulary is closed

Every animation a sequence can draw comes from a fixed list: `PROP_IDS`
(`question-mark`, `sparkle`, `sweat-drop`, `battery`, `sunglasses`) in
`packages/character/src/rig.ts`. The comment is the rationale: each member "is
artwork this package draws, so a sequence can never ask for a prop that does not
exist and no caller can inject arbitrary content into the scene". The renderer
draws only these (`packages/character/src/render.ts`, `PROP_PATHS`). A sequence
also declares the `assets` it can draw, "used to assert nothing leaks"
(`packages/animation-engine/src/types.ts`).

### 3. The model never chooses an animation

The model cannot emit an animation id, a script or a style. It emits only the
**application events** in the closed `APPLICATION_EVENTS` list
(`packages/contracts/src/events.ts`). A single auditable function maps those to
the character's machine events — `machineEventForStreamEvent` in
`packages/animation-engine/src/index.ts` — and the widget feeds the result to the
animator (`packages/widget/src/widget.ts`, `#onStreamEvent`). The animator exposes
only `dispatch(event: MachineEvent, now)` and `play(group, now)`; there is
"deliberately no API that takes an animation id from a model response, so a
compromised or over-eager model cannot drive the character past the vocabulary the
application compiled in" (`packages/animation-engine/src/engine.ts`).

### 4. Model output is rendered as text, not markup

The widget never uses a template string for network data. `el()` is the only
element builder, and it sets values with `textContent` (`packages/widget/src/dom.ts`):
"a model that emits `<img onerror=...>` renders it as those literal characters
rather than as markup". Assistant text is appended with `textContent`
(`widget.ts`, `#appendTurn`). The **one** `innerHTML` in the widget is `setSvg`,
whose input is SVG generated by `renderSunny` from a rig the widget computed —
"never a string from a server or a model" (`dom.ts`).

Two more layers make this structural rather than a convention:

- Every SSE frame is validated against `chatStreamEventSchema` before it is used,
  and an unrecognised frame is **dropped, not thrown** (`packages/widget/src/chat.ts`).
- The client "never reads a script, selector or URL out of the stream"; the only
  server-supplied value that reaches the DOM is a page-action _target name_
  (`chat.ts`, header comment).

### 5. `suggest_page_action` is confined to named landmarks

The tool's contract already restricts its arguments: a page action is
`highlight | scroll | navigate | focus | open_panel`
(`PAGE_ACTIONS`, `packages/contracts/src/events.ts`) and the `target` is "a key
the HOST resolves; **never a selector or a URL**" (`packages/contracts/src/chat.ts`).
The server validates both before emitting an event (`apps/api/src/agent/tools.ts`,
`suggest_page_action`).

The client is where the confinement is enforced, and it is a **map lookup, not a
selector**:

- `DEFAULT_LANDMARKS` is a fixed map of names to selectors
  (`quote-form`, `savings-calculator`, `contact-details`, `pricing`,
  `case-studies`) in `packages/widget/src/widget.ts`.
- `#applyPageAction` drops anything not in `PAGE_ACTIONS` and resolves the target
  only through that map — "a selector, a URL or any other free-form target is not
  resolvable and is ignored" (`widget.ts`).
- `navigate` will only follow an `href` read **from the resolved host element**,
  and only if it is relative or same-origin. "A URL from the model is not accepted,
  so a page action can never become a redirect to an attacker's site"
  (`widget.ts`).
- The highlight is applied by setting an attribute (`data-sunny-highlight`) and
  removing it after 4 s; the widget "injects no style or a class of its own into
  the customer's DOM" (`widget.ts`). The demo host page styles the attribute
  itself (`apps/widget-demo/public/index.html`).

## Consequences

- The isolation is containment by construction: a landmark allow-list, a closed
  prop list, a closed event list, and a single text-only render path. Each is
  checkable, and each is commented with its rationale at the point of use.
- Because the shadow root is `open`, a hostile _host page_ can reach into it. That
  is intended — the host already controls the page — and it is why the model's
  output never becomes DOM behaviour in the first place.
- The widget still needs CORS to talk to the API. Origin is checked in a Fastify
  `onRequest` hook and at session creation (`apps/api/src/server.ts`), but the
  session request's `origin` is contractually **advisory** ("a browser can be told
  to lie", `packages/contracts/src/widget.ts`); the real control is that the token
  grants only visitor-scoped reads.
- The character renders into the launcher and the panel header from one
  `requestAnimationFrame` loop, and identical frames are skipped by comparing
  markup strings (`widget.ts`, `#startFrameLoop`, `#renderCharacter`) — a
  performance choice that also means no work is done when the character holds a
  pose.

## Alternatives considered

- **An iframe.** The plan offered it, and it would give stronger origin isolation
  and a real document boundary. Not chosen: it makes the panel sizing, the
  landmark highlighting on the host page, and the open/close transition across a
  document boundary substantially harder, and the Shadow DOM approach already
  removes the style collision — the actual, observed failure — while the model-driven
  hazards are handled by the closed vocabularies regardless of container. This
  choice should be revisited if a concrete cross-site constraint (for example, a
  host page whose CSP forbids inline shadow styles) demands it.
- **A template-literal renderer.** Rejected; `dom.ts` exists specifically to make
  `textContent` the only path.
- **Letting the model pass a CSS selector, validated server-side.** Rejected: a
  named landmark the host resolves is a smaller, auditable surface than any
  selector validator.
- **Firebase App Check as the origin defence.** Not adopted. The discovery doc
  records a hard limit — App Check "does not support web apps that serve on more
  than 250 domains" — which a multi-tenant embed across arbitrary customer domains
  would exceed; support beyond that is **UNVERIFIED**
  (`docs/discovery-google-services.md` §6, item 9). App Check is never treated as
  the sole defence (§9 of the plan).

## Open questions

- **Unknown — needs verification:** behaviour of the Shadow DOM widget under a
  strict host Content-Security-Policy (e.g. one that disallows inline styles),
  and whether an iframe would be the better fallback for those hosts. Not tested.
- **Unknown — needs verification:** whether App Check can be used at all for the
  embed-on-customer-domains case given the 250-domain ceiling
  (`docs/discovery-google-services.md` §6).
- `landmarks` can be overridden via `MountOptions` (`packages/widget/src/widget.ts`)
  "used by the visual tests" — but there is no visual test suite in the repository
  yet (`tests/` is empty), so the override is currently only a fixture seam.
- The plan (§8) asks for "visible stop control" for guidance and "explicit
  confirmation for consequential actions". Today `navigate` is the only
  consequential action and it is constrained to host-provided same-origin links;
  there is no separate confirmation step.
