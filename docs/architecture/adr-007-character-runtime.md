# ADR-007: Character animation runtime — Rive, authored by an animator

- **Status:** Amended 2026-10-12 and 2026-10-14 — see "Amendment" sections below
- **Date:** 2026-10-12

## Amendment (2026-10-14, owner direction)

The owner found the in-house character moved "like a slideshow" and rejected
its hands and feet. Still in-house (Rive was considered again and declined),
with three changes to the runtime:

- **Compositing.** `animation-engine/src/compositor.ts` blends from the last
  drawn rig into each new target (180 ms; 260 ms into a state's loop), lays the
  blink over the frame as an eyelid overlay instead of letting it win, and
  trails the body with damped springs so rays and hands follow through. Every
  state now has a resting loop.
- **Frame rate.** Body motion runs at the display rate; the 24 fps film clock
  is kept for the ink boil, and for motion only on low-power devices.
- **Anatomy.** Limbs come out of sockets between the rays instead of morphing
  rays (`character/src/limbs.ts`), with hands and shoes built from shapes
  (`character/src/hands.ts`) rather than traced from the pose sheet.

## Amendment (2026-10-12, owner direction)

The owner asked for Sunny to mimic the reference artwork as a 1930s
rubber-hose cartoon ("Cuphead vibe") and to redraw it in-house rather than wait
on an animator, and supplied `reference_poses.png` showing the full body. The
production character is therefore the traced reference (`traced-art.ts`,
generated by `scripts/trace-reference.py`) with rubber-hose limbs
(`limbs.ts`), animated in code on 24 fps film frames with a boiling ink line
(`cartoonClock`). `@sunny/character-rive` is kept, dormant, as an upgrade path
if a Rive file is ever commissioned. The decision below is the original record.

- **Related:** ADR-005 (widget isolation), `docs/EVALUATION.md` §3.1–3.2, plan §3.1, §5

## Context

The current character is drawn procedurally: `@sunny/character` computes SVG
path strings from measured proportions and `@sunny/animation-engine` produces a
new rig every frame, which the widget and the marketing hero assign with
`innerHTML`. The evaluation of 2026-10-12 found that this approach:

- does not reproduce the reference artwork closely (line weight, cheek creases,
  smile, highlights);
- has no limbs — the "ray-to-arm morph" is a stretched triangle — so none of the
  flagship sequences can be staged as the plan describes;
- produces stiff, low-amplitude motion, and rebuilds the DOM every frame.

The owner's requirement is **high-quality animation** in the spirit of the
mascot. Character animation of that standard (rubber-hose limbs, mesh
squash-and-stretch, props, comic timing) is drawn by an animator, not computed.
The plan already names Rive as the preferred runtime (§3.1: "Rive interactive
rig + GSAP/Motion/SVG as needed").

## Decision

1. **Sunny is a Rive file authored by an animator** from `sunny.png`, following
   `docs/design/rive-animator-brief.md`. The procedural rig is retired as the
   production renderer.
2. **The application keeps the behaviour; Rive owns the drawing.** The existing
   state machine (`machine.ts`), priority scheduler and event vocabulary stay in
   `@sunny/animation-engine`. They drive the Rive state machine through a fixed,
   versioned input/event contract (brief §5). The model still never names an
   animation (ADR-005).
3. **One integration package**, `@sunny/character-rive`, wraps the Rive web
   runtime: loading, canvas sizing, device-pixel ratio, pausing off-screen and
   on hidden tabs, reduced motion, intensity, theme colour, and the contract.
   The widget, marketing site, dashboard Studio and the lab all use it.
4. **Lazy loading.** The core character file loads with the launcher; prop- and
   game-heavy sequences live in separate files loaded on first use.
5. **Fallback.** Until the `.riv` file is delivered, and whenever it fails to
   load, the widget shows a static vector of the reference at rest. The host
   page keeps working (plan §6.2).

## Consequences

- The animation quality ceiling is set by the animator, not by code.
- A person must be engaged (contractor or in-house); this is the critical path
  for milestone M1.
- The Rive runtime (WASM) adds weight to the widget. Budget: measure on the
  first delivery and keep the launcher's first paint independent of it (static
  vector first, Rive swapped in once ready).
- Visual regression tests switch from byte-comparing generated SVG to comparing
  rendered frames at named contract checkpoints, after human sign-off.
- `@sunny/character` geometry and the per-frame sequence functions in
  `sequences.ts` become legacy and are removed once the Rive path covers the
  flagship sequences.

## Verified (2026-10-12)

Checked against Rive's documentation and the published npm packages on
2026-10-12, with runtime version **2.44.2** pinned:

- **Runtime package: `@rive-app/canvas-lite`.** Rive publishes `webgl2`
  (Rive Renderer, the only one with Vector Feathering), `canvas` (Canvas2D),
  `canvas-lite` (Canvas2D without the text, layout, audio and scripting
  engines; the smallest), `canvas-single` (WASM inlined into the JS) and the
  deprecated `webgl`. All share one API. Sunny needs none of the engines
  `canvas-lite` drops, and Canvas2D has no per-page context limit, which
  matters for a widget that may share a page with other canvases. The brief
  forbids the features this runtime cannot draw.
  Source: https://rive.app/docs/runtimes/web/canvas-vs-webgl,
  https://rive.app/docs/runtimes/web/web-js
- **Size:** the `canvas-lite` package ships `rive.wasm` at 772 KB
  uncompressed (`npm pack --dry-run`). It is fetched only when the Rive Sunny
  mounts, never with the launcher's first paint. By default the runtime
  fetches it from unpkg; `RuntimeLoader.setWasmUrl()` self-hosts it, which
  production should do (no third-party CDN on installers' pages).
  Source: https://rive.app/docs/runtimes/web/preloading-wasm
- **Contract mechanism: data binding.** Rive Events are documented as
  "DEPRECATED: Use Data Binding instead of Events", and state machines are
  "indirectly controlled through transitions conditioned on Data Binding
  properties". The contract is therefore one view model (`SunnyVM`,
  `autoBind: true`) whose enum, number, boolean, color and trigger properties
  the app writes, plus triggers the file fires and the app observes with
  `.on()`. Color properties take an ARGB integer (`0xFF000000` is opaque
  black). Sources: https://rive.app/docs/runtimes/web/rive-events,
  https://rive.app/docs/runtimes/web/data-binding,
  https://rive.app/docs/runtimes/web/state-machines
- **Constructor:** `stateMachine` (single string, v2.41.0+) supersedes the
  deprecated `stateMachines`; `onLoad` / `onLoadError` callbacks;
  `resizeDrawingSurfaceToCanvas()` handles device-pixel ratio; `play()` /
  `pause()` (pause keeps the last frame); `cleanup()` frees WASM objects.
  Source: https://rive.app/docs/runtimes/web/web-js, the package's `rive.d.ts`
- **Licence:** all the web runtime packages are MIT (`npm view`).

The brief's §5 was revised to match: data binding only, enum states by name
rather than numbered, and Rive → app signals as view model triggers instead
of Rive Events.
